# Privacy audit: promises against what the code does today

Date: 2026-10-21. Method: reading the code, the policies, the seeders, the docs and the test names. Nothing was changed in the app, and no test was written or run for this audit. Where a row says "from reading", the claim is not proven by a test, so treat it as plausible, not certain.

Update 2026-10-22: promises 2 and 8 are now built (SCR-044 and SCR-045), with tests. Rows 2 and 8 below were rewritten; every other row is as audited on 2026-10-21.

Rule used: a promise may be published only when the verdict is **Yes**. Anything else needs a code change (through an SCR), a different promise, or a written internal rule.

| # | Promise you plan to make | Verdict | Evidence in the code | What is missing or wrong |
|---|---|---|---|---|
| 1 | Client files are visible only to the assigned team | **Partly** | `MediaPolicy::view` allows a brief file only when `BriefPolicy::view` allows it, and a project file only when `ProjectPolicy::view` allows it. Both mean: an admin who holds `briefs.view` or `projects.view`, or a member of the client's own organization (project not in draft). Contributors have no branch in either policy, so they cannot open brief files or project files. Tests: `PrivateFileAccessTest` ("denies other organizations, contributors and admins without brief access", "serves project files only to the owning organization once the project is visible, and to project admins"). | **The Groibe side is not limited to the assigned team.** `PermissionMatrix` gives briefs `rua` to delivery managers and `r` to community managers, and projects `crua` to delivery managers and `r` to community managers and finance. So every delivery manager, community manager and finance user can open any client's files, assigned or not. **The client side is the whole organization** (owner, manager and viewer), not a team. **Contributors do reach client files in one way:** files attached to project messages (`MessagePolicy`, project thread audience: seated contributors with an `active` or `completed` seat). Honest wording today: "visible to your organization, to the Groibe staff who run projects, and to contributors seated on your project for files shared in project messages". |
| 2 | Contributors never see client names or rates | **Yes, built** (SCR-044, 2026-10-22) | **Names:** `AuthorLabel::for` now labels a client author "Client" for a contributor, and `AuthorLabel::forTaskComment` does the same on task pages. Notifications and emails to contributors carry the project title and their role only. **Rates:** no contributor or shared screen reads `contract_value`, `budget_band` or `total_value`; a contributor sees only their own payouts. Tests: `tests/Feature/Privacy/ContributorSeesNoClientIdentityTest.php` (19 cases: every thread page, task page, contributor notification and email, with a negative test per page; six of them fail on the old code), `MessagePostingTest`. | Not covered by code: text a person types (project title, scope, task text, messages, file names and contents). Keeping a client name out of that text is a staff rule, and the commitment should say so. Clients and admins still see client people by first name and organization, by design. |
| 3 | Files only through short-lived signed links | **Yes** (with notes) | Route `files/{media:uuid}` has `verified`, `signed` and `throttle:60,1`. The link lasts `groibe.uploads.signed_url_minutes` = 10 minutes. The controller still calls `Gate::authorize('view', $media)`. Responses carry `Cache-Control: private, no-store` and `X-Content-Type-Options: nosniff`. Storage names are random ULIDs on the private `local` disk, with no `storage:link`. Tests: `PrivateFileAccessTest` (login and signature required, expired link rejected, cannot be guessed by id, not reachable through any public path), `SubmissionFileAccessTest` (the same for submission files, other file's signature refused). | Notes, not breaks: (a) the link is not tied to one person: it proves the app issued it, and the sign-in plus policy decide. (b) Profile photos are served by a signed-in route (own photo only), not a signed link. (c) A person who may view a file can save it, and the promise cannot cover what they do after. (d) The data-export file is made on the spot and never stored. |
| 4 | Access ends when an assignment ends | **Mostly** (from reading) | `RemoveAssignment` returns the person's unfinished tasks to unassigned. `ThreadAudience`, `Project::messageableBy` and the contributor board only count seats that are `active` or `completed`, so a removed person loses the conversation (test: `ThreadAccessTest` "loses access on the next refresh when the seat is removed"). `TaskPolicy::work` needs an `active` seat. A suspended contributor is refused everything (`before()` in the policies). | (a) `RemoveAssignment` leaves **approved** tasks attached to the removed seat, and `TaskPolicy::view` checks only who holds the task, not the seat status. So a removed contributor may still open their approved tasks by link. (b) `MediaPolicy` lets a contributor read their **own** submission files with no seat check, which may be intended ("their own work"), but it is not stated. (c) A **completed** seat keeps read access to the project board and thread, with no end date (by design, spec 6.2 and 14). Say so in the promise: "when your seat is removed" and "after completion, read-only access to your own work". No test covers (a) or (b). |
| 5 | No client data used to train AI | **Yes today, but not enforceable by code** | The app makes no outbound calls except email. There is no AI package and no HTTP client use in `app/` or `config/`. Spec 21 puts AI out of scope. `CLAUDE.md` forbids real personal data in the repo and in demo data. | (a) The placeholder `app/Services/Ai` named in spec 21 and in `CLAUDE.md` does not exist in the repo (a spec and code mismatch, harmless). (b) The promise is also about what **people** do: staff or contributors pasting client files into an outside AI tool, and any tool the founder or a developer uses. Only a written rule, a clause in the Member Agreement and the Client MSA, and processor terms can cover that. (c) If AI features are ever added, this promise needs a new SCR first. (d) Public wording: `CLAUDE.md` bans AI-related wording in public copy, which conflicts with stating this promise on the site. Your decision. |
| 6 | Export and erasure requests | **Yes, built** (with limits) | `/settings/privacy` and Admin, System, Data requests (SCR-028). `PrepareDataExport` builds the JSON on the spot, never stored. `UserAnonymiser` erases name, email, password, sessions, profile and photo, skills, application text, proof-of-work text, support conversations, notifications and the address on email log rows, and soft-deletes the account. Refused while work or money is open. A reminder goes to super admins after 7 days. Tests: `AnonymiseUserTest`, `DataRequestActionsTest`, `DataRequestScreensTest`, `UserDataExportTest`. | (a) The legal deadline for answering is not set (OPERATIONS section 2: lawyer to confirm). (b) Erasure **keeps** payouts, the audit log, project messages and comments, submissions, published reviews, agreement acceptances and reputation figures. The policy must say so, and the lawyer must confirm each. (c) **Backups are not erased:** weekly dumps (4), pre-deploy dumps (5), the host's daily backups and the off-server copies (8 weekly, 3 monthly) keep a person's data until they age out. (d) Only a signed-in account holder can ask. A person who cannot sign in has no route. (e) There is no screen for **correction**, **withdrawing consent**, **grievance** or **nominating** someone, which the Act may expect: lawyer to say what is needed. (f) No request path for a **company's** data as opposed to a person's. |
| 7 | Retention rules | **Partly** | Built and tested (DEPLOY section 18, SCR-032, SCR-034, SCR-039): email log `sent` 90 days and `failed` 180 days; failed jobs and job batches 30 days; read notifications 180 days; audit log 365 days (minimums 7, 7, 30 and 90); import files 30 days; log files 14 days; weekly dumps keep 4; pre-deploy dumps keep 5; expired password-reset tokens daily. | **No rule and no job** for: client briefs, project files, submission files, project messages, applications, reviews, contact messages (visitor personal data, deleted only by hand, super admin), accounts of people who left, soft-deleted users (kept forever, anonymised), and the host's and off-server backups. A promise "we keep client files for N months after the project" cannot be made until the lawyer sets N and a job is built. Names and emails can also sit in `activity_log` properties for up to 365 days. |
| 8 | Audit log of file downloads | **Yes, built** (SCR-045, 2026-10-22) | `LogFileDownload` writes an `activity('file')` entry with the person, the media id, the collection, the display name, the size and the time. It is called by `MediaDownloadController` (brief, project, submission and message files), by the client SOW PDF and print routes, and by the admin SOW PDF action. It runs only after the policy allows the request. Tests: `tests/Feature/Security/FileDownloadAuditTest.php` (18 cases: each file collection and each SOW route; denied access, guest, bad signature, expired link, guessed id and missing file write nothing; contents and stored path are never in the entry). | (a) The entries are pruned with the audit log, 365 days by default (minimum 90), so "who opened this file" is answerable for that long only. (b) Profile photos are not logged (own photo on every page; the public photo is public). (c) A person who may view a file can save it, and the log cannot say what they did after. (d) Whether clients may ask to see the record of their own files is not decided (lawyer and founder). |
| 9 | Processors list: MilesWeb, Cloudflare, email provider, Zoho Books | **Incomplete** | MilesWeb: hosts the app, the database, the files, the cron and the host's backups (DEPLOY). Cloudflare: DNS now, and the proxy at go-live (DEPLOY section 11): it sees all traffic, including addresses. Email provider: whatever `MAIL_HOST` points to, not yet chosen for production (STAGING_CHECKLIST D2). Fonts are self-hosted, and tests check there are no third-party requests. | Missing from your list: **GitHub** (code only, private; it must never hold real personal data); **off-server backup storage** (encrypted with gpg, kept by the founder); the **uptime monitor** (sees only `/up`); the **password manager**; the **mail provider for staff mailboxes** (client emails and attachments pass through it); any tool used to read or edit client files. **Where each is located** (country of the MilesWeb servers, Cloudflare's global network) is not stated anywhere and matters for transfers: the lawyer needs it. A written agreement with each processor is a business task, not code. |

## Summary

- **Safe to promise now:** 2 (contributors never see client names or rates, built), 3 (signed links), 6 (export and erasure, with the limits listed) and 8 (download audit log, built, kept for the audit retention period). Number 5 only as a statement of what the platform does today.
- **Promise only with changed wording:** 1, 4, 7, 9.
- **Do not promise until built:** none of the original eight remains in this group. Promise 7 still needs retention periods and jobs.
